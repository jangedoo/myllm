Model and assumptions

Loss fit

The five histories were smoothed with a trailing 20-step mean and sampled approximately uniformly in log-token space. The fitted two-factor power law is:

L(N,D) = min(ln(49,152), 7.0722·N−0.6175 + 10.2060·D−0.1499)   where N and D are in millions

Throughput fit

The calculator infers the nearest architecture produced by the current MyLLM depth/width rule, applies the repository's training-FLOP estimator, then converts achieved compute into token/s. GPU utilization is modeled as saturating with per-token work:

achieved TFLOP/s = 46.325·(1 − exp(−FG/0.05207));   token/s = achieved FLOP/s ÷ F
  • This is an empirical training-loss fit, not a universal scaling law and not a validation-loss predictor.
  • Perplexity is calculated as exp(final loss).
  • Only five runs are available. Model size varies, but every run stops near 100M tokens, so token extrapolation is especially uncertain.
  • The reliable interpolation region is 6.49M–70.85M parameters and 1M–100M tokens. The page still calculates outside it but displays a warning.
  • The loss ceiling is ln(vocab_size), corresponding to the 49,152-token vocabulary's near-uniform initial prediction.
  • All calibration runs use MyLLMV1, tied embeddings, head dimension 128, FFN width 4× model width, RoPE, causal SDPA, BF16, fused AdamW, cosine LR, sequence length 1,024, micro-batch 32, and gradient accumulation 5.
  • The throughput baseline assumes the logs were produced on PyTorch GPU 0: NVIDIA RTX PRO 4000 Blackwell (24,467 MiB). The host also has an RTX 2070 SUPER (8,192 MiB), but the artifact metadata does not store the device name.
  • Throughput estimates assume the same software stack and training recipe. They exclude startup/compile overhead, data bottlenecks, checkpoint time, evaluation, memory limits, and multi-GPU communication.
  • Architecture inference is discrete. An arbitrary parameter input is mapped to the nearest architecture generated by the repository's depth-to-width rule; the entered parameter count itself is still used for loss prediction.
  • Training time is simply total tokens divided by estimated steady-state token/s. It is not a wall-clock guarantee.
